# Repository functional audit

This is the exhaustive audit ledger for the repository. It separates observable
product functionality from implementation abstractions so that a passing helper
test is never mistaken for a working user flow.

Snapshot date: 2026-09-05.

## Inventory boundary

The current executable surface contains:

- 113 FastAPI operations across 18 `/api/*` route groups;
- 34 leaf CLI commands;
- 13 MCP tools and 3 MCP resources;
- 10 React router entries (including compatibility redirects and fallback);
- 319 production Python files, with 252 top-level classes and 826 public
  top-level functions;
- 108 production frontend JavaScript/JSX files;
- 211 backend and 22 frontend test files.

The API's exact operation list is generated by `create_app().routes`; the CLI's
exact command list is generated by recursively walking `build_parser()`. Those
composition roots, rather than prose, are authoritative when this ledger and the
code disagree.

authorises a write to their Zotero library.

## Abstraction audit

The abstraction pass is distinct from the functional runs. For every production
class and public top-level function, the audit records its callers, owning layer,
contract/invariant, and the functional IDs that exercise it. Definitions with no
runtime caller must be justified as framework registration or removed. Duplicate
or cyclic abstractions are assessed with the repository's existing import,
redundancy, overlap, dead-code, LOC, and slop checks before any new tooling is
considered.

The current class distribution is:

| Area | Top-level classes |
|---|---:|
| API | 31 |
| Contracts/domain/runtime/settings | 8 |
| Integrations | 36 |
| MCP | 1 |
| Models | 76 |
| Services | 93 |
| Storage | 7 |
| **Total** | **252** |

The first whole-tree abstraction scan completed with `orphans=0`, two
redundancy candidates, two swallowed-exception findings, and 50 deterministic
function-overlap candidates. The final scan ran through the project environment,
including vulture, and exposed seven candidates. Caller tracing classified two
as real external/dynamic consumers and five as production-dead surfaces (A215).

Every one of the 50 overlap pairs was then inspected. Most are deliberately
separate schema validators, explicit FastAPI handlers, provider adapters, or
small field accessors whose names carry different contracts. The strongest
mechanical clusters are Zotero key generation, JSON sidecar read/write,
collection resolution, score normalization, and the two prewarm schedulers.
The prewarm resolvers already share `_flight.resolve_prewarm_k`; the remaining
clusters are recorded as consolidation candidates rather than hidden behind a
new generic base/helper. A004 records the resolution of the two exact clone and
two swallowed-exception scan results.

## Completion rule

This audit is complete when every F-row has three dated, independently run
checks with preserved command/output evidence; every production abstraction is
covered by caller/static analysis and mapped, justified, or recorded as a
finding; and the repository's final guardrails have been run. Confirmed defects
are audit outputs, not implicit authorization to mutate production behaviour;
fixing them at shared roots with focused regression tests is a separate
implementation phase. Environment failures are reproduced and isolated rather
than silently waived.
