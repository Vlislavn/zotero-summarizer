# Структура настроек: меньше решений, а не больше раскрывающихся блоков

## Исправление выбора моделей — 2026-11-03

```text
Сохранённое использование задач → Изменить нужную задачу
  → сохранённое подключение → модель → явные задачи → влияние → сохранить
  → отдельно проверить выбранные сохранённые модели
```

Сводка показывает фактические модели трёх задач, а не только default. Default /
fallback — отдельное назначение; явные overrides не сбрасываются. Сохранённые
подключения различимы по имени, Local/Hosted и точному адресу. Адрес, API и доступ
остаются в контекстных деталях; ключи — у прежнего отдельного владельца. Connect
может сохранить пока не используемое подключение; Cancel не удаляет его и не
отменяет уже сохранённый ключ или отправленный запрос.

Проверка одной задачи или сохранённого выбранного набора явно называет модели и
не запускает Doctor/работу со статьями. Один tiny prompt не доказывает structured
output, длинный контекст, PDF или качество обзора. UNKNOWN локальной безопасности
остаётся отказом: отсутствующее runtime-доказательство нельзя получить сменой URL.
Ревизия, stale-результаты и HOLD сохраняются; Telegram не переназначается.

Применены прежние решения критиков и lenses Hick/Tesler/recognition: убран
обязательный вход через серверную администрацию, scope виден до сохранения,
проверка не выдаёт default за все рабочие маршруты. Исходные критики и captures:
`data/model-settings-ux/20261103-review/`; текущие проверки исправления:
`data/model-settings-ux/20261103-fix/`. Нижеследующие counts, PNG и ACCEPT относятся
к историческим срезам, **не квалифицируют это исправление**.

PASS; lint и disposable build PASS. Визуально перепроверены saved/scope/test/

## 2. Как выглядит обычный визит

Условные значения; пользовательская конфигурация не читалась.

```text
Настройки

Обработка       AI включён · сохранённая конфигурация     [Изменить]
Подключения     Zotero · доступ к полным текстам           [Управлять]
Язык результата Русский                                   [Изменить]
```

Это не три блока, под которыми постоянно лежат все старые формы. Пока ничего не
редактируется, нет обязательного прохождения шагов, матрицы Feed/Backlog/Deep
review, пресетов неподключённых сервисов, токенов, temperature или калибровки.
Наличие исключений обозначается кратко; подробное влияние раскрывается **когда
изменение действительно может их затронуть**. Ошибка и понятное восстановление
остаются видимыми; «сохранено» не выдаётся за проверенную работу.

Количество строк здесь — следствие выбранных обязанностей, не правило Hick.
Существующий [Ease Health](../frontend/DESIGN.md) сохраняется.

**Следующее уточнение пользователя:** API/endpoint-настройка непонятна даже
разработчику. Перенос формы не решает эту проблему. Обычное подключение не должно
требовать знания provider registry, `api_key_env`, Default и stage routing.

```text
Уже настроено: сохранённый сервер · выбранная модель       [Изменить]

Добавить OpenAI-совместимый сервер
  Адрес API [ http://localhost:11434/v1                    ]
            [Подключить сервер]

Выбрать модель [ полученные имена                       v]
              [Использовать как основную]
```

**Убрать из обычного пути:** ручные внутренние идентификаторы и имена env-переменных,
повторный выбор сервисного/аппаратного профиля, назначение каждого наследующего
этапа, temperature/thinking/token-поля. Сохранённые параметры не стираются;
ProviderConfig/registry/factory/keyring остаются единственными владельцами.

**Это две разные операции:** добавить неиспользуемое подключение, затем явно
назначить выбранную модель. Первая не меняет текущие default/stages; вторая показывает
вычисленное влияние и сохраняет исключения, включая отдельный Telegram-маршрут.
Новый адрес уже используемого provider сначала становится отдельным неактивным
кандидатом: запись в старый provider сразу изменила бы действующие задачи.

Внутренний контракт должен быть определён, хотя пользователь не видит его таблицу:

```text
черновик → зарегистрирован, не используется → каталог / ручной ID
                                          → влияние → выбор сохранён
credential записан отдельно → ошибка/отмена не обещает его откат
потерян ответ → точный readback, не повтор записи вслепую
```

Для keyless loopback-сервера ключ не обязателен независимо от точки входа. Но
loopback ≠ отсутствие авторизации: discovery сейчас намеренно использует non-secret
local token, а обычный inference может иметь реальный credential. Недоступный
каталог защищённого сервера допускает ручной ID, не ложный «успешный вход».

Не обещать универсальность: native Anthropic выбирается до регистрации и может
иметь `base_url=None`; custom proxy-path сохраняется, `/v1` не дописывается слепо.
Новый remote-адрес не получает существующий секрет до явного подтверждения точного
назначения. Сам факт нахождения provider в config не равен согласию пользователя.
Настоящий no-auth remote пока требует отдельного изменения resolver-а, не фиктивного
ключа. Для bootstrap без валидного default неизвестному custom remote нельзя
обещать обычную предварительную регистрацию: нужны явный ID/полный config либо
отдельный контракт первой регистрации, без подставной модели.

Destination approval, listing, impact и commit привязаны к текущим ревизиям
config/auth/profile. Замена общего credential slot учитывает всех его потребителей.
Сохранённый выбор не равен operational/hardware-safe; реальный тест — отдельно,
с сохранением отказа UNKNOWN и без автозагрузки/повторов/fallback.

Полные CAPA/переходы/receipts: `data/settings-research/connection-20261027.OQlQA4/`.

## 3. Система берёт на себя координацию, а не смысл

```text
Пользователь решает                 Система обязана сделать
что исследовать                    не подменять цель догадкой
какие источники читать             сохранить выбранный состав/область
какую модель использовать          применить существующее наследование
разрешить конкретную работу        показать её пределы и затем результат
```

- При смене default система рассчитывает влияние на эффективные назначения,
  сохраняет явные исключения и показывает значимые последствия. Пользователь
  не восстанавливает их вручную и не назначает каждый наследующий этап заново.
- Для поддержанных подключений используются уже существующие пресеты, обнаружение
  путей и сохранённые значения. Никакой новой «умной» автоматизации не объявляется
  готовой; новые endpoints, модели, облачные маршруты и разрешения не выбираются молча.
- Технические лимиты используют текущие сохранённые/валидированные значения. Для
  обычного запуска не предлагается заново настраивать шесть числовых полей.
  Пределы работы видны человеческим описанием; точные overrides доступны по месту.
- Настройка источника, его запуск и результат — одна связная задача. Не переносим
  исходную длинную форму целиком на Today/Weekly и не заставляем обходить несколько
  разделов ради сохранения и запуска. Рабочий экран открывает редактор по запросу.

## 4. Два коротких сценария

**Изменить AI:** Settings → «Изменить» → новая модель текущего подключения →
система показывает затронутые назначения → сохранить. Без повторного выбора
режима, Zotero, целей и всех этапов. Проверка с inference — отдельное явное действие.
Telegram сохраняет отдельный локальный маршрут, без fallback на общий/облачный.

**Добавить Telegram-источник:** Weekly → «Источники Telegram» → добавить/сохранить →
явно согласиться на ограниченный сбор и обработку → открыть полученный отчёт здесь
же. Исторические отчёты остаются неизменяемыми. Для RSS аналогичный цикл начинается
в Today, но fetch и triage остаются разными явно запрашиваемыми этапами.

Подключения и повторный вход можно исправить из текущей задачи с возвратом в неё.
Это **те же канонические редакторы**, а не независимые реализации на каждом экране.
Первоначальный Setup остаётся необязательным и не становится пропуском к обычной
работе с источниками, ML-only или чтению.

## 5. Что нельзя решить перестановкой экранов

**Найдены два независимых исследовательских намерения:**

```text
Основной config             research_goals + triage_criteria
Research-feed profile       themes + projects → Telegram Interests
```

Сейчас изменение целей в Settings не означает изменения интересов Telegram-обзора.
Опоры: `services/research_feed/profile.py:25–51`, `models/research_feed.py:121–139`,
`services/research_feed/telegram_review.py:160–169` (относительно
`zotero_summarizer/`). Ни один из трёх исходных дизайнов полностью это не покрывал;
родитель нашёл разрыв по первичному коду, независимый reviewer подтвердил.

**На ближайшем изменении сохранить оба смысла и явно назвать область:**
«Отбор статей» в Today, «Интересы обзоров» в Weekly. Отдельный web-редактор второго
профиля — новая возможность, не уже существующая часть Sources. Не обещать один
общий профиль, не синхронизировать автоматически, не добавлять третью иерархию
профилей. Возможное объединение требует отдельного решения с просмотром конфликтов.

Другие необходимые контракты перед реализацией:

- **Scoped save:** нынешний config — полная запись; перенос форм без merge/conflict
  защиты может затереть соседние изменения. «Один редактор — одно сохранение»
  требует настоящего владения изменениями, не только новых кнопок.
- **Частичные overrides:** provider и model наследуются независимо. Сохранить поля
  исключения не значит сохранить эффективную пару после смены default. Влияние
  надо вычислить; автоматически закреплять или сбрасывать значения нельзя.
- **Shared provider:** его endpoint может затронуть несколько задач и Telegram.
  Изменение подключения нельзя представлять как локальное изменение одного экрана.
- **Recovery:** сохранённое `collecting` — последнее наблюдение, не доказательство
  живой работы. Нужны проверка состояния/владения и доступный snapshot; не слепой
  повтор, бесконечный disabled или обещание, что закрытие браузера остановило сервер.
- Credentials имеют отдельный эффект, пути требуют restart. «Отмена» не должна
  обещать откат уже записанного credential. Unknown/partial и согласие не удаляются.

## 6. Почему выбран этот путь

```text
A: настройки только для предпочтений → сильнее связывает источник и результат
B: центральное workspace по объектам → сохраняет адрес, но рискует каталогом вкладок
C: обзор + задачи изменения          → убирает onboarding, но рискует мини-wizard
```

Выбран **A как направление**, с прямыми задачами изменения/исправления из C и одним
каноническим владельцем каждого редактора. Не выбираем «самую короткую страницу»:
если перемещение заставит искать настройки по всему приложению, оно не принято.

B не выбран как основной: «Исследование / AI / Источники и доступ» организует тот же
каталог, а разрыв RSS edit→Today добавляет переходы. C не выбран целиком: его обзор
снова содержит большинство подсистем и может оказаться прежней формой, разбитой
на обязательные шаги. Это экспертное сравнение, не измеренные результаты usability.
Независимая проверка также предпочла A **условно**, указав неполноту intent и recovery.

Первый проход про summary-first/подписи остаётся полезен локально, но **больше не
считается достаточным структурным ответом**. Его точные bytes сохранены в
`data/settings-research/structure-20261027.TM8uVL/research-before.md`.

## 7. Как отличить сокращение от маскировки

В прототипе пройти смену AI с частичным override; добавление RSS с последующим
triage; Telegram save→consent→run→partial/result; возвращение после потери статуса.
Проверять: не повторяются ли известные ответы, не нужно ли вручную согласовывать
экраны, понятны ли область настройки, последствия и результат. Не считать успехом
просто меньше раскрытых полей, меньше вкладок или зелёную сборку.
