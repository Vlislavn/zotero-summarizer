# Как предотвращать ошибки агентского кодинга: исследование guardrails

Дата исследования: 2026-09-06. Источники: официальная документация, оригинальная
статья автора подхода и исследовательские публикации. Это исследование подходов,
не отчёт об их внедрении. Remote, branch protections и полномочия CI не проверялись.

## Вывод

Нужен не ещё один длинный prompt, а разделение **создателя изменения и механизма
его приёмки**, плюс ограничения на реальные побочные эффекты. Агент может
предлагать изменение проверок, но не должен единолично ослаблять обязательный
критерий приёмки своего изменения. Это инженерный вывод из механизмов ниже,
а не доказанная универсальная методика предотвращения всех AI-generated bugs.

Четыре разных уровня нельзя выдавать за одну гарантию:

| Уровень | Что означает | Чего не означает |
|---|---|---|
| Статическое отклонение | Проверяемая программа нарушает типовой или архитектурный контракт | Python не сможет исполнить этот код без проверки |
| Предотвращение runtime | Запрещённая операция отвергается на границе DB/OS/парсера | Все разрешённые операции семантически правильны |
| Блокировка merge | Изменение нельзя принять без обязательного результата проверки | Проверка обнаруживает любой дефект |
| Вероятностное обнаружение | Генерация примеров/последовательностей или мутации повышают шанс найти дефект | Успешный прогон доказывает отсутствие дефектов |

## 1. Независимый проверяющий контур, а не самосертификация агента

GitHub поддерживает required status checks, обязательное одобрение code owners,
сброс устаревших approvals и указание GitHub App, от которого принимается статус.
По умолчанию у администраторов возможен обход branch protection. Статусы
`skipped` и `neutral` могут удовлетворять required check: само имя обязательного
job не доказывает, что проверки действительно выполнялись.
См. [официальные правила protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

Практическое следствие: workflow, обязательные контрактные тесты, конфигурация
проверок, allowlist и сам CODEOWNERS — отдельная защищённая поверхность изменений.
Обязательный итоговый job должен отвергать отсутствие обязательных результатов,
а не превращать пропуск в успех. Выбор trusted App защищает происхождение статуса,
но сам по себе не защищает содержание редактируемого workflow. CODEOWNERS требует
включённого обязательного review; GitHub отдельно рекомендует защищать сам файл
CODEOWNERS. [Документация code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

Минимальное применение: существующие проверки оставить, но определить небольшой
набор защищённых контрактов безопасности и данных. Их изменение требует
независимого одобрения. Не запрещать агенту писать обычные тесты и не вводить
новую approval-процедуру для каждого файла. Если работа остаётся полностью
локальной, аналогичная граница должна находиться вне записываемого агентом
workspace; локальный hook, который агент может изменить, не независимый арбитр.
Это рекомендации, а не утверждение о текущих настройках репозитория.

## 2. Убрать способность совершить запрещённое действие

Для сценария «только предложение» сильнее отсутствие writer-доступа, чем флаг
`dry_run`, который каждый вложенный вызов обязан помнить. SQLite `mode=ro`
открывает базу read-only. `PRAGMA query_only=ON` отклоняет CREATE, DELETE, DROP,
INSERT и UPDATE, но допускает checkpoint/COMMIT и не является полной read-only
изоляцией. [SQLite URI](https://www.sqlite.org/uri.html),
[query_only](https://www.sqlite.org/pragma.html#pragma_query_only).

Минимальное применение: вычисление предложения получает только нужные входные
данные/read-only доступ; применение решения — отдельный разрешённый путь записи.
Существующий модуль записи переиспользуется, универсальный capability-framework
не нужен. Один Python-процесс с доступным глобальным writer может обойти такое
разделение: тип Protocol или read-only wrapper — не security sandbox.

Для тестового запуска, которому вообще не нужна сеть и пользовательские файлы,
границу можно вынести в отдельный ограниченный процесс/контейнер. Docker
`--network none` оставляет только loopback; `--read-only` относится к корневой
файловой системе, а явно writable mounts остаются writable. Следовательно,
нельзя выдавать контейнеру пользовательские секреты, writable библиотеку или
Docker socket и продолжать считать его изолированным.
[Сеть none](https://docs.docker.com/engine/network/drivers/none/),
[параметры контейнера](https://docs.docker.com/reference/cli/docker/container/run/).
Это пример механизма, не предложение немедленно добавлять Docker в приложение.

## 3. Недопустимые состояния должны отвергаться до бизнес-логики

Подход **parse, don’t validate** сохраняет результат проверки в более строгом
типе вместо возвращения прежнего неструктурированного значения. Тогда изменение
предположения становится видимым вызывающему коду. Оригинальная статья показывает
это на статически типизированном Haskell; её compile-time гарантии нельзя
автоматически приписывать Python.
[Alexis King, Parse, don’t validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/).

Для Python практическая комбинация — runtime parsing на входе и статическая
проверка дальнейшего кода. Pydantic discriminated unions выбирают модель по
явному tag и отвергают неправильный/отсутствующий tag. Mypy с `assert_never`
или включённым `exhaustive-match` обнаруживает необработанные варианты.
[Pydantic unions](https://docs.pydantic.dev/latest/concepts/unions/#discriminated-unions),
[Mypy exhaustiveness](https://mypy.readthedocs.io/en/stable/literal_types.html#exhaustiveness-checking).

Применение: `не проверено`, `ошибка`, `проверено без совпадений` — разные состояния,
а не `{}` и bool; выбор конкретных объектов не смешивается с явным «все»;
действие `read/skim/skip` не представляется произвольной строкой. Это защищает
форму и полноту обработки, но не доказывает истинность evidence. `Any`, unchecked
casts и обход runtime parsing ослабляют эту границу.

Инварианты хранилища должны жить также в SQLite: `NOT NULL`, `CHECK`, `UNIQUE`,
foreign keys. Они проверяют записи независимо от вызывающего service/API.
Важные пределы: CHECK с результатом NULL проходит; foreign keys нужно включать
для каждого connection; проверки можно отключить привилегированным кодом.
[SQLite constraints](https://www.sqlite.org/lang_createtable.html#check_constraints),
[включение FK](https://www.sqlite.org/foreignkeys.html#fk_enable).

## 4. Архитектура как проверяемый запрет зависимостей

Import Linter forbidden contracts проверяют не только прямые, но по умолчанию
и косвенные импорты, включая дочерние модули. Layers задают направление
зависимостей. Это подход **architecture-as-tests**, а не обязательный выбор
именно этого нового инструмента.
[Forbidden contracts](https://import-linter.readthedocs.io/en/latest/contract_types/forbidden/),
[layers](https://import-linter.readthedocs.io/en/latest/contract_types/layers/).

Минимальное применение здесь: опираться на существующую проверку layering,
добавляя только доказанно недостающий запрет: например, proposal-код не зависит
от writer-кода. Проверка графа импортов не анализирует реальные эффекты
callbacks, global state и динамических импортов. Поэтому она дополняет, но не
заменяет runtime запрет записи и интеграционный тест.

## 5. Контрактные properties и последовательности вместо только happy path

Property-based testing генерирует входы для заданного свойства; stateful testing
генерирует также последовательности действий. Официальный пример Hypothesis
сравнивает настоящую базу с небольшой независимой моделью и выдаёт сокращённую
последовательность, воспроизводящую расхождение. Документация прямо замечает,
что для простых случаев state machine не нужна — достаточно обычного `@given`.
[Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html).

Минимальные свойства для данного класса приложения:

- Размер конечного контекста не превышает бюджет, включая все разделители.
- Proposal/read/dry-run не меняют защищённые таблицы и внешнюю библиотеку.
- Ошибка до публикации не заменяет последний пригодный результат.
- Последовательность start → retry → cancel → restart не публикует результат
  чужого запуска и не расширяет исходно выбранное множество объектов.

Это кандидаты контрактов, не утверждение об уже выполненных тестах. Модель
ожидаемого поведения должна выводиться из пользовательского требования, а не
копировать алгоритм реализации. Генерация конечна и ограничена strategies;
плохое свойство даёт ложную уверенность при любом количестве примеров.
Генерация последовательностей также не равна исследованию всех thread schedules.
При проверке запрета записи нельзя подменять mock-ом сам потенциальный writer:
нужен реальный service/storage путь на временных данных, с подменой внешних
провайдеров на границе.

## 6. Проверять, что guardrail способен поймать свою ошибку

Mutation testing вносит искусственные дефекты и проверяет, обнаруживают ли их
тесты. Исследование Just et al. обнаружило статистически значимую связь между
обнаружением mutants и реальных дефектов независимо от code coverage; это
корреляция на исследованных системах, не гарантия для этого Python-приложения.
[Оригинальная публикация FSE 2014](https://homes.cs.washington.edu/~mernst/pubs/mutation-effectiveness-fse2014-abstract.html).
Более поздняя работа исследовала почти 15 миллионов mutants и наблюдаемое
улучшение тестов разработчиками; её вывод нельзя превращать в обещание, что
mutation score устраняет все баги.
[Does mutation testing improve testing practices?](https://arxiv.org/abs/2103.07189).

Минимальное применение: целевые мутации критических контрактов — убрать cap,
разрешить writer в dry-run, принять unknown как negative, опубликовать failed
artifact. Каждая такая мутация должна вызвать релевантное падение защищённого
теста, а не случайную ошибку импорта. Выжившая мутация требует разбора:
тест слабый, путь не покрыт либо изменение эквивалентно. Не требовать слепо
100% общего mutation score. Mutmut — существующий Python-инструмент;
его документация описывает выбор мутируемых путей и влияние ограничений
глубины тестового стека на число выживших mutants.
[Mutmut](https://mutmut.readthedocs.io/en/latest/).

## Практический порядок применения, не список новых зависимостей

1. Независимо зафиксировать небольшой набор запрещённых исходов и защитить
   изменение проверяющего контура. Сначала проверить реальные полномочия CI.
2. На наиболее опасных путях убрать лишнюю возможность записи; формальные
   ограничения входа и хранилища исполнять там, где их нельзя забыть в caller.
3. Покрыть эти контракты реальным интеграционным путём и properties;
   stateful-проверки добавить только для ошибок порядка событий.
4. Подтвердить чувствительность тестов целевыми мутациями и сделать результат
   обязательной приёмкой. Быстрые локальные проверки дают feedback агенту;
   защищённый CI решает, можно ли принять изменение.

Это снижает классы ошибок, а не обещает, что они «никогда не возникнут».
Семантическая корректность LLM-ответов по-прежнему требует независимого oracle
и содержательных evals: валидный JSON и существующая цитата не доказывают,
что вывод следует из статьи.

## Репозиторий: подтверждённые причины и отсутствующие guardrails

Исследовательский снимок **до исправления A139**: проверены dirty worktree поверх
`7e156af`, конфигурация локального CI, выбранные тесты и история двух изменений.
Это анализ механизмов появления и
пропуска дефектов, **не атрибуция мотивов конкретному агенту**: полные траектории
исходного кодинга не исследовались. Статусы Axxx взяты из
[функционального аудита](functional-audit.md); уже исправленные находки ниже
используются как исторические примеры, а не объявляются открытыми повторно.

| Свидетельство | Почему ошибка могла пройти | Предотвращающий контракт |
|---|---|---|
| A139: [worker](../zotero_summarizer/services/library/deep_review.py) после сохранения review вызывает `quality_gate.fire_for_keys`; gate затем записывает метки | Общая операция анализа приобрела эффект записи, несовместимый с обещанием вызывающего fleet. Локальная корректность gate не обеспечивает безопасность композиции | Proposal не имеет полномочий менять метки; реальная цепочка uncached review → storage сохраняет защищённые таблицы неизменными |

Проверки пустоты, повторов и внеобластных ключей на всех входных поверхностях |
| [Fail-fast hook](../.claude/hooks/fail_fast_reminder.sh) выдаёт `additionalContext`; [slop checker](../tools/precommit/check_slop.py) оставляет swallowed/silent-recovery advisory | Напоминание о запрете не исполняет запрет. Название guardrail и длинный текст не обеспечивают отказ операции | Точные запрещённые AST-паттерны возвращают nonzero; допустимые фоновые error-boundaries имеют отдельный проверяемый контракт, а не тотальный запрет любого catch |
| A125/A137 и A212 уже исправлены: ранее бюджет нарушался в отдельных ветках, а regex пропускал формы импорта | Не было достаточной проверки общего инварианта на разных путях и самой способности проверяющего инструмента отказать | Для cap — независимое свойство конечного размера во всех потребителях; для import gate — отрицательный корпус синтаксиса и мутации обхода. Текущий AST gate всё ещё не проверяет runtime effects |

### Историческая причинная цепочка A139

`git log -S` показывает: sidecar-only тест появился в `c94f8b9` (2026-06-26),
а `fire_for_keys({item_key})` добавлен в общий worker в `3997d2a` (2026-07-10).
`git show` подтверждает вставку непосредственно после `_try_rebuild_render`.
Таким образом, защитный тест существовал до расширения побочных эффектов, но
его подмена общего сервиса не могла обнаружить этот новый эффект. Это конкретное
свидетельство недостаточного контроля контрактов callers при изменении callee;
оно не устанавливает, кто и с какими намерениями написал изменение.

Проверочный прогон 2026-09-06, без изменения кода:

```bash
KMP_DUPLICATE_LIB_OK=TRUE .venv/bin/pytest -q --forked \
  tests/test_review_fleet_propose.py::test_evaluated_goal_miss_allows_dont_read_on_skip \
  tests/test_review_fleet_job.py::test_job_writes_sidecar_but_never_label_verdicts \
  tests/test_quality_gate.py::test_only_keys_scopes_l2_but_l1_still_applies_everywhere
```

Результат: **5 passed, 5 warnings, 17.70s, exit 0**. Это подтверждает зелёный
статус выбранных ошибочных/неполных проверок, а не исправность функций. Полный
backend повторно не запускался: в этом исследовании изменён только этот документ.

В последующем проходе устранения A139 скрытый label-hook и его scoped API удалены;
реальные caller-to-SQLite тесты и две целевые мутации заменяют пропущенный контракт.
Старая проверка scoped L1 и ожидание silent skip больше не являются действующими
тестами: причины пересмотра и результаты приведены в
[отдельной записи аудита](functional-audit.md#2026-09-06--a139-review-completion-no-longer-applies-labels).
Исторический RCA выше сохранён, а не переписан так, будто дефекта не было.

Позднее A143/A144 также закрыты: явный выбор сохранён от клиента до worker,
пустой список не запускает работу, дубликаты нормализуются в общих точках входа.
Интеграционные проверки, три целевые мутации и полный baseline-сравнённый прогон
записаны в [аудите](functional-audit.md#2026-09-06--a143a144-explicit-review-selection).
Это исполняемые регрессии в обычном CI, не внедрение независимого защищённого verifier.

### Что действительно проверяет текущая среда

[CI](../.github/workflows/ci.yml) запускает pre-commit, backend pytest и frontend
lint/tests/build. В этом workflow и [dev dependencies](../pyproject.toml) нет
обязательного Python type checker или отдельного mutation gate. Это не означает,
что в репозитории совсем нет property-проверок: текущий
[test_context_budgets.py](../tests/test_context_budgets.py) уже содержит независимые
ограниченные переборы без нового фреймворка.

[tests/conftest.py](../tests/conftest.py) изолирует Settings/runtime, убирает
унаследованные ключи и подменяет Python TCP connect. Это полезная защита обычного
pytest-прогона, но не OS sandbox для subprocess/native-кода. В `.github/` найден
только workflow; состояние удалённых rulesets и других настроек не проверялось.

## Как должен выглядеть цикл именно во время кодинга

Важно различать запрет действия и обнаружение после него. В Claude Code
синхронный `PreToolUse` с `permissionDecision: "deny"` блокирует вызов инструмента;
`additionalContext` только передаёт текст модели. Асинхронный hook не может
блокировать действие. Поэтому pytest после записи файла — раннее обнаружение,
а не предотвращение появления неправильного исходника.
[Документация hooks](https://code.claude.com/docs/en/hooks#pretooluse-decision-control),
[ограничения async hooks](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background).
Это механика Claude Code, не свидетельство исполнения `.claude` hooks в текущей
сессии Codex. Один запрет для edit-tool также не закрывает запись через shell:
политика должна охватывать все доступные пути, а её настройка — быть защищённой.

Предлагаемый процесс — инженерный вывод из исследования, не уже установленная
автоматизация:

1. **До реализации:** сформулировать несколько проверяемых запретов от лица
   пользователя и явно указать разрешённые эффекты операции. Например,
   `proposal не меняет label_verdicts`, `[] не запускает работу`,
   `failed retrieval не превращается в отрицательный вердикт`.
2. **До исправления:** независимый проверяющий подтверждает смысл этих контрактов
   и проверяет, что тест действительно воспроизводит дефект. Для новой функции
   отсутствие реализации должно давать ожидаемое падение; для guardrail нужен
   заведомо запрещённый вход. Не принимать случайный ImportError как доказательство.
3. **После изменений:** доверенная среда автоматически запускает быстрые
   контрактные проверки затронутой границы. Ошибка возвращается агенту как
   обязательная работа, а не advisory. Перед приёмкой требуется успешный прогон
   на точном проверяемом состоянии кода; последующие изменения обнуляют результат.
4. **Перед приёмкой:** выбранная опасная мутация должна быть обнаружена;
   защищённый verifier проверяет реальные результаты и обязательные команды.
   Агент может предложить пересмотр контракта, но не принять собственное
   ослабление без независимого решения. Для локальной работы этот арбитр должен
   находиться вне доступной агенту на запись среды.

У Anthropic есть первичный инженерный отчёт о согласовании sprint contract
до написания кода и отдельном evaluator, который проверяет работающее приложение,
API и состояние БД. Он также отмечает склонность к положительной самооценке и
то, что отдельный LLM evaluator сам по себе её не устраняет. Это полезное
свидетельство подхода, но не контролируемое доказательство универсальной
эффективности и не жёсткая граница безопасности.
[Harness design for long-running application development, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps).

**Начать здесь стоит с трёх контрактов: отсутствие скрытых записей, сохранение
области выбранных ключей и запрет unknown → hide.** Они непосредственно закрывают
опасную связку A139/A140/A143. Сначала доказать, что проверяющий контур отвергает
эти нарушения, затем исправлять реализацию. Не начинать с нового универсального
agent framework, массовой переписи типов или множества проверяющих агентов.

Отдельный предел для A122/A134/A135: источник цитаты, точное совпадение span и
версию документа можно проверять детерминированно; логическое следование
произвольного ответа из цитаты этим не доказывается. LLM judge здесь остаётся
вероятностной оценкой. Жёстко можно ограничить последствия: не превращать
неподтверждённый ответ в автоматически применённую метку или иной опасный эффект.
